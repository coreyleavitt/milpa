# RFC: compile-time-checkable dependency graphs

**Status**: Stub
**Author**: Corey Leavitt
**Companion to**: `coreyleavitt/fresco/docs/roadmap-compile-time-research.md`, `coreyleavitt/fresco/docs/rfc-intonaco-fresco-split.md`

## Why this RFC exists

milpa today (v0) emits `nim.cfg` with `--path:` lines. The compiler trusts that file: if a path is missing, `import X` fails with a confusing "cannot open file" error at the point of import, not at the point where the dep graph was wrong.

The fresco/intonaco compile-time-first thesis says: *if a property can be enforced at compile time, the substrate enforces it at compile time, not at runtime*. Dep-graph correctness is exactly such a property.

This RFC proposes that milpa emit not just `nim.cfg` but also a **typed Nim representation of the resolved dep graph** — a generated `milpa_graph.nim` file consumed by the project at compile time. The graph is then a compile-time-checked artifact: typos in transitive-dep names, missing srcDir entries, version mismatches against expected exports — all become *compile errors*, not runtime resolver failures or mysterious import failures.

## Sketch

```nim
# generated by milpa fetch
import std/sequtils

type
  MilpaDep* = object
    name*: string
    source*: string         # URL or registry
    sha*: string            # commit hash or content hash
    srcDir*: string

const milpaGraph*: seq[MilpaDep] = @[
  MilpaDep(name: "chronos", source: "https://github.com/...",
           sha: "...", srcDir: ""),
  MilpaDep(name: "intonaco", source: "https://github.com/...",
           sha: "...", srcDir: "src"),
  ...
]
```

Then the consumer's main module can:

```nim
import milpa_graph
static:
  doAssert milpaGraph.anyIt(it.name == "chronos"),
    "milpa: chronos dep missing — run `milpa fetch`"
```

A macro `assertDep` makes this ergonomic:

```nim
import milpa_graph/assertDep
assertDep("chronos", minVersion = "4.2.0")
# expands to a static block that checks at compile time
```

## Theoretical contribution

The depend-on-graph property is well-known but never enforced at compile time. Standard tools (cargo, npm, pip) emit "configuration data" (paths, locks) that the build system trusts implicitly. By emitting *typed Nim code* that the compiler statically verifies, milpa bridges the gap between "resolver output" and "compile-time-checked dep contract."

Generalizes beyond Nim: any compiled language with a macro/codegen story could adopt the same pattern. Rust's `build.rs` + emitted `*.rs` files; Zig's `@import("build_options")`; C++'s constexpr graph constants.

## Deferred until

- milpa v0 is shipping (PubGrub + content addressing) so the *resolution* primitives exist
- One additional milpa-using project exists (sinopia or amoxtli) so the multi-consumer story is tested

## Open questions

1. How does this interact with `nim check` (which doesn't run main, doesn't see runtime imports)?
2. What's the right place to fail — compile-time of `milpa_graph.nim`, or compile-time of the consumer that imports it?
3. Can we extend to "this dep must export symbol X" via Nim's `typeof` and `compiles()` introspection?
