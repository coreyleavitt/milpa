## 1  Problem

A routine `milpa fetch` in a downstream consumer (`amoxtli`) fails with
`FETCH-PROVENANCE-DIVERGENCE` on deps that were never touched. The proximate
cause is a content-hash mismatch; the root cause is a **single-source-of-truth
violation in an identity algorithm that should never have been hand-rolled in
the first place.**

### 1.1  Evidence — the same bytes hash three ways

`bearssl` v0.2.8 @ commit `22c6a76`, identical source, three milpa generations:

| Producer | content_hash | scheme |
|---|---|---|
| tianguis `index.kdl` (≤ Jun 7) + every downstream lock | `sha256:7bdfea3c…` | flat working-tree |
| milpa binary built Jun 22 | `sha256:6ddd9062…` | flat working-tree (post-churn) |
| milpa HEAD (`7341d34`, object-store) | `sha256:7caf0450…` | flat object-store |

The lockfile `identity` and the index `content_hash` agree with **each other**
(`7bdfea3c`) — they are *not* two skewed schemes, as first hypothesized. The
outlier is the *running binary*, and HEAD is a third value again. Identity has
churned ≥3 times pre-1.0 with no migration discipline and no self-describing
epoch, so a stale hash is indistinguishable from a wrong one — which is exactly
what turned a routine churn into a multi-day diagnosis.

### 1.2  Root cause — identity is a bespoke *algorithm*, re-implemented outside its authority

`spec/identity.md` is normative: *"Any implementation that claims milpa
conformance MUST produce byte-identical hashes."* milpa already keeps its
Python and Rust impls at zero divergence via the `conformance/spec-v1/` corpus
and the harness. The defect is that the algorithm has **a fourth implementation
that escaped that authority**, and the spec's own evolution discipline assumed
it could not exist:

1. **Two freelance producers.** `tianguis/src/tianguis/vendor/driver.nim:84`
   (git clone path) *and* `tianguis/src/tianguis/vendor/realdriver.nim:31` (OCI
   adopted-author path) compute index `content_hash` via tianguis's *own*
   `identity.nim` (`computeContentHash` over a working-tree directory) — never
   via milpa. The index is *authored* by one hasher and *verified* by another.
   Worse, tianguis's `identity.nim` includes the executable bit in the hash
   (`MODE_EXECUTABLE = 0x01`), while milpa epoch 1 *excludes* it — so the two
   already disagree on any tree containing an executable file, independent of
   the object-store change.

2. **A frozen-snapshot conformance test.** `tianguis/tests/test_identity.nim`
   checks identity against `tests/fixtures/identity_conformance.json` — a
   *local copy* "generated by running milpa's algorithm," not the live
   `conformance/spec-v1/` corpus. The copy goes stale silently the moment
   milpa's algorithm moves. It did.

3. **A git-free parity fixture (differential blind spot).** That test's
   `materializeTree` writes plain files and reads them back — pure working-tree
   semantics, no git. It is *structurally incapable* of catching the
   object-store-vs-working-tree divergence introduced by `7341d34`.

4. **A falsified spec premise.** `spec/identity.md §1.7.6` invokes
   `spec_versioning_deferred`: *"milpa is pre-1.0 with no external consumers;
   the spec is mutated in place… the pre-fix hashes… carry no compatibility
   obligation."* This is false. tianguis is an external consumer, and the
   published `index.kdl`/`index.json` plus every downstream `milpa.lock` are
   compatibility-bound state.

The deeper observation: **none of this drift would be possible if identity were
a primitive instead of a procedure** (§2). The bug is the occasion; the redesign
is the fix.

## 2  Prior art — the two escapes, and milpa's synthesis

| System | Identity | Cross-impl drift? | Transport model |
|---|---|---|---|
| cargo / crates.io | SHA-256 of the `.crate` **tarball bytes** | None | single canonical transport |
| uv / PyPI | SHA-256 of the **wheel/sdist file bytes** | None | single canonical transport |
| git | Merkle tree/blob object hashes | None | is the substrate |
| OCI | descriptor **digests** (multihash) over a Merkle manifest | None | content-addressed by construction |
| IPFS | **CIDs** (multihash + multicodec) over a UnixFS Merkle DAG | None | content-addressed by construction |
| **milpa (today)** | bespoke flat null-separated byte-stream → sha256 | **yes (this RFC)** | **multi-transport** |

**Escape #1 — cargo/uv: identity as a primitive.** Identity is the SHA-256 of
*opaque artifact bytes* — a primitive that Rust, Nim, and Python compute
identically with zero shared code, so there is no algorithm to drift. **But it
is transport-bound**: the hash is of *the tarball*, and crates.io is the *one*
canonical transport. milpa's thesis is the opposite — many transports for the
*same logical source* with transport-independent identity and cross-transport
dedup (`spec/identity.md §1.1`). Artifact-bytes identity would fragment identity
across transports and kill dedup. milpa is right to refuse it.

**Escape #2 — git/OCI/IPFS: identity as a canonical Merkle DAG.** Every system
that *does* content-address across heterogeneous representations converged on a
**canonical Merkle-DAG digest with a self-describing multihash**. Hashing a DAG
whose leaves are content blobs is *also* close to a primitive — the only shared
logic is a small, structural tree-node encoding, far easier to keep
byte-identical than a bespoke whole-tree walk. milpa's flat concatenation
(`§1.2`) is a worse reinvention of this.

**milpa's synthesis (this RFC).** Take cargo/uv's *primitive* discipline and
git/OCI/IPFS's *Merkle-DAG transport-independence*, and unify all impls under
*one conformance authority*. Identity becomes a canonical content Merkle DAG,
digested as a self-describing scheme string, with a thin per-transport
materializer as the only transport-specific surface — and every
producer/consumer (milpa-py, milpa-rust, tianguis, future nim) bound to the live
corpus. This is transport-independent content-addressing that none of the
incumbents have *because none of them are multi-transport*. It is milpa's actual
research contribution, worth doing properly rather than patching a fourth copy
of a flat hash into agreement.

## 3  Design

### 3.1  Principles

- **P1 — One algorithm, one authority.** The normative identity algorithm is
  defined by `spec/identity.md` and *enforced* by `conformance/spec-v1/`. There
  is exactly one authority; no implementation carries a private snapshot of it.
- **P2 — Every implementation is bound.** Each producer/consumer of identity is
  bound to the live corpus by **delegation** (obtain the hash from milpa via a
  stable oracle surface) or **gating** (run the live corpus in its own CI). A
  freelance hasher is a bug.
- **P3 — Identity strings name their scheme; epochs are migrated, never mutated.**
  The identity string's prefix names the *full canonical computation* (scheme +
  digest), not just the hash function. Any change is a new *epoch* shipped via a
  clean cutover with a coded migration condition — never an in-place mutation. A
  stale hash is then *detectable as old-epoch*, not merely *wrong*.
- **P4 — Identity is a canonical Merkle DAG, not a bespoke walk.** Content is
  addressed as a Merkle DAG of blobs and tree-nodes (§3.4). The cross-impl
  surface collapses to a thin transport materializer + a small canonical node
  encoding, both corpus-gated; identity aligns with git/OCI/IPFS; and shared
  subtrees become dedupable.

### 3.2  Scheme naming (P3) — replaces "untagged = legacy"

The current `sha256:<hex>` prefix names the *hash function*, not the scheme.
Both the flat walk and the Merkle DAG use sha256; the distinguishing variable is
*what was fed to sha256*. The prefix must therefore name the scheme.

**Pre-v1, breaking changes are expected, and there is a single controlled
consumer set (Corey's own projects + tianguis).** So milpa ships **no legacy
support whatsoever** — no intermediate `flat-sha256:` scheme, and no read-only
accommodation of the old bare `sha256:` strings. There is exactly **one valid
scheme**: `dag-sha256:<64-hex>` (the Merkle DAG, §3.4). Everything else —
including a pre-cutover bare `sha256:<hex>` — is simply **not a scheme milpa
understands**, and `parse_identity` rejects it as `ID-UNSUPPORTED-ALGORITHM`
(§3.5) like any other unknown prefix. This is *not* a special legacy path: it's
the absence of one. We do not carry a `LEGACY_SCHEMES` tier, a dedicated
"legacy" error, mixed-epoch lock tolerance, or a `[legacy — re-lock]`
annotation — that is exactly the migration scaffolding pre-v1 lets us skip.

The self-describing-prefix value of P3 survives for free: because the prefix
names the *scheme*, a stale `sha256:` hash surfaces as a **coded
`ID-UNSUPPORTED-ALGORITHM`** (whose message names the offending prefix and says
"re-lock with `milpa fetch`"), never as a silent `FETCH-PROVENANCE-DIVERGENCE`.
That coded-not-silent property — the entire lesson of the multi-day diagnosis —
needs only the prefix, not a legacy-accommodation apparatus. The one-shot
B-cutover regen replaces every `sha256:` string in the corpus, the registry, and
every lock; after it, no live artifact carries a non-`dag-sha256:` identity, so
there is nothing to "support."

> The digest stays raw 32-byte/64-hex (not a varint-prefixed binary multihash):
> the scheme prefix already names the algorithm, so a multicodec varint would be
> redundant. B1 confirms this; `dag-sha256:` is **not** an IPFS CID (§3.6).

### 3.3  The SSOT resolution (P1+P2) — one producer, reached through one oracle

tianguis must stop computing identity independently. With a Merkle-DAG algorithm
the case is decisive: a second, hand-ported Merkle-DAG hasher in Nim is exactly
the kind of duplicate that just failed.

**Mechanism — delegate to a narrow milpa oracle.** Introduce `milpa hash
<source>` (slice A0). It **MUST be implemented as `FetcherRegistry.fetch(prov,
dest=scratch)` → print `result.identity` → discard scratch** — i.e. it *is*
`milpa fetch` minus CAS-admission and the lockfile write, calling no
identity-computation function directly. That architectural pin (not "equivalent
logic") is what makes the oracle provably identical to a real fetch and forecloses
a fresh SSOT violation. Source forms:

- `milpa hash git=<url> ref=<commit-sha>` — fetch + materialize (object-store
  path) + print. `ref` **MUST be a full commit SHA**, not a branch/tag, or the
  output is non-deterministic; a symbolic ref is resolved and the resolved SHA
  printed alongside. This is the form **tianguis uses** (both `driver.nim` and
  `realdriver.nim`), because object-store materialization is what milpa's own
  fetch does — hashing tianguis's *working-tree checkout* would reintroduce the
  smudge divergence.
- `milpa hash local=<path>` — hash an on-disk tree directly (no fetch). For
  local deps, debugging ("which file moved my hash?"), and corpus tooling.
  **Carries a health warning**: it uses the local/working-tree materializer, so
  for a git checkout it is *not* equivalent to `git=` (no object-store
  normalization). To hash from an already-cloned repo's object store without a
  re-fetch, B1 may add `git-local=<repo-path> ref=<sha>`.

`parity.yaml` already clones and runs milpa, so the binary is present in CI; the
publish/vendor workflow installs it likewise.

> **Considered and rejected for the oracle surface:** (i) a `--print-identity` /
> `--hash-only` flag on `milpa fetch` — `fetch` operates over a *manifest*, not a
> single source, so it would need the same new source-spec parser anyway; a
> named `milpa hash` is the narrower, clearer surface. (ii) "registry-as-publisher"
> (tianguis reads identity from a full `milpa fetch`) collapses to the same
> delegation — *something* must invoke milpa when vendoring; `milpa hash` is just
> the minimal way to do it.

**tianguis stops being a hashing implementation at all.** Because the delegation
removes every call site, `tianguis/src/tianguis/identity.nim`, its
`tests/test_identity.nim`, and the frozen `tests/fixtures/
identity_conformance.json` snapshot are **deleted outright** (subject to a usage
audit — `IdentityDrift` in `namespace.nim` is namespace identity, unrelated).
There is then exactly *one* producer of content identity in the whole ecosystem
(milpa), reachable through one oracle. "Bind the second hasher to the corpus" is
moot when there is no second hasher — the single-source-of-truth discipline
taken to its end.

> **Why delegate over a corpus-gated native Nim hasher** (the alternative,
> consistent with how milpa-py/milpa-rust are bound): the Merkle-DAG algorithm
> is materially more complex than a flat walk (tree construction, materializers,
> submodule recursion), and tianguis *only* needs "the hash milpa would
> compute." Maintaining a 4th native implementation through every epoch — the
> very thing that just broke — is not worth it for a consumer with no
> independent hashing need. The oracle surface (`milpa hash`) is the one
> authority entry point; the corpus remains the conformance authority for the
> *impls* (py/rust) that genuinely re-implement. **Notable decision — flag if
> you disagree** (§6).

### 3.4  The canonical content Merkle DAG (P4 — epoch 2)

> §3.4 gives a **candidate** normative shape precise enough to review for
> collision-resistance and cross-transport determinism. B1 freezes it as a
> byte-level table in `spec/identity.md`.

**Blob node** — a regular file's bytes, or a symlink's target string.
`H_blob = sha256(content-bytes)`. **Transport-neutral** (F-resolved-A): *not*
git's `blob <len>\0…` object hash. The git materializer streams committed blob
bytes via `cat-file --batch` and runs one sha256 pass — zero marginal I/O (the
bytes are already read to materialize), one CPU pass per blob; identical cost to
the tarball/local path. Content rules inherit epoch 1: raw bytes, no line-ending
normalization (`§1.2`), symlink content is the target string (`§1.5`),
non-UTF-8 relpath rejected (`ID-NON-UTF8-RELPATH`).

**Tree node** — the canonical encoding of one directory's entries. Candidate
entry encoding, per entry:

```
<uint32-be name-length> <name-bytes> <mode-byte> <32-byte child-digest-raw>
```

entries (both blob and subtree children) concatenated in **ascending UTF-8 byte
order of `name`** — the *leaf name*, a single path component, **not** the full
relpath (this differs from epoch 1's full-relpath sort, §1.3, and is the highest
cross-impl-divergence risk: the builder MUST re-sort children by leaf name at
each level and not rely on the materializer's stream order). `H_tree =
sha256(concat(entries))`. Length-prefixing the name removes any separator-byte
ambiguity (a name may contain any non-NUL byte); B1 sets a normative name-byte
ceiling (`name ≤ 4096 bytes`, else a coded error). The child-digest is the raw
32-byte sha256 (not the ASCII `dag-sha256:` string) — compact, and the
self-describing string lives only in lockfiles, never inside a node.

**Mode-byte** — **four-valued in epoch 2**: `0x00` regular, `0x01` executable,
`0x80` symlink, **`0x40` tree (subdirectory child)**. The fourth value is
load-bearing (round-2 C1): a tree node mixes blob and subtree children, both
carried as a raw 32-byte digest, so the mode byte is the **type tag** that
domain-separates `H_blob` from `H_tree` inside a parent (the
Certificate-Transparency `0x00`/`0x01` leaf/node discipline). Without it the
encoding cannot represent subdirectories *and* a blob could forge a subtree.
With it, the encoding is sound (length-prefix kills name ambiguity; the mode
byte separates the digest space; sha256 covers the residual). The mode byte also
**includes the executable bit** (`0x01`) in identity for the first time — a
deliberate epoch-2 correction: epoch 1 dropped it, so two trees differing only
in a script's `+x` hashed identically (a real correctness hole). git tracks it
(`100644`/`100755`), the materializers already have it, tianguis's hasher
already included it. **Notable decision — flag if you disagree** (§6, N2).

**DAG construction** — materializers yield a *flat, fully-buffered*
`(relpath, mode, bytes)` sequence (git `ls-tree -r`; or a directory walk). It is
**not** a streaming hash feed: the builder must collect the whole sequence
(bounding peak memory to "entries + one blob"), then group by directory prefix
and construct tree nodes **bottom-up** — deepest directories hash first, each
producing an `H_tree` that becomes a parent entry (mode `0x40`), up to the root.
The root `H_tree` is the identity. At every level the builder **sorts the
immediate children by leaf name** independently (see above). B1 specifies this
in pseudocode with a **pinned non-trivially-nested fixture** (≥2 levels, where
leaf-name order ≠ full-path order) carrying a hand-computed `dag-sha256:` digest,
so both impls implement against a frozen oracle rather than against each other.

**Empty directories & empty root** — a tree node with zero entries contributes
**no entry** to its parent, applied recursively (an intermediate directory empty
after the rule is itself omitted), keeping git (no empty dirs) and tarball/local
byte-identical. The **empty source tree** is therefore the zero-entry root:
its identity is normatively `dag-sha256:` of `sha256("")` =
`dag-sha256:e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`.

**`.git/` exclusion** — `§1.4`, inherited: any path component named `.git` is
excluded before DAG construction.

**Submodules** — a gitlink entry has no blob in the parent object store; it is
materialized by fetching the submodule (per `§1.7.5`, *not* zero-cost) and its
root `H_tree` is spliced in as the child-digest of a tree entry at the gitlink's
path. B1 specifies this; the "near-zero-cost git materializer" framing applies
only to submodule-free repos.

Properties: **transport-independence among faithful transports** (the DAG
derives from content — but only transports that carry the full content model
agree; a `.zip` that drops POSIX exec bits, or any lossy archive, materializes a
*genuinely different* tree and hashes differently. B2-tarball states this: milpa
prefers exec-bit-bearing formats (tar); a lossy archive is a different tree, not
a hash bug); **subtree dedup** (shared subtrees share an `H_tree`, exploited by
the split-out CAS work); **substrate alignment** (git/OCI/IPFS are all
Merkle-addressed); **collapsed drift surface** (only the node encoding + DAG
builder + materializer are shared logic, all corpus-gated).

### 3.5  Migration model (P3) — clean cutover, no legacy support

Earlier drafts proposed a dual-emit window (lockfiles carrying both epochs) and,
later, a read-only "legacy scheme" tier. **Both dropped.** Pre-v1, with one
controlled consumer set, the right amount of migration machinery is *none*: a
one-shot regen (B-cutover) is already acceptable, so milpa never carries code to
keep old hashes working. Instead:

- milpa advances to epoch-2 emission in one release. The lockfile schema is
  **unchanged** (single `identity` field; only the string's scheme prefix
  differs).
- **Two-tier scheme classification — canonical or unsupported.** `parse_identity`
  accepts exactly `CANONICAL_SCHEMES = {dag-sha256}` and rejects **everything
  else** — including the old bare `sha256:` — as `ID-UNSUPPORTED-ALGORITHM`.
  There is no `LEGACY_SCHEMES` set and no dedicated legacy error. A stale
  `sha256:` lock is *unsupported*, full stop; its coded error message names the
  prefix and says "re-lock with `milpa fetch`".
- **Rejection is at parse, before any disk/CAS work.** Because an unsupported
  scheme fails in `parse_identity` itself, every operation that reads a locked
  identity (`fetch`, `lock`, `verify`, `--frozen`) surfaces
  `ID-UNSUPPORTED-ALGORITHM` *before* a `store.contains()` lookup or a member
  drift-comparison — so a stale lock never masquerades as a misleading
  `FROZEN-IDENTITY-NOT-IN-STORE` / `FROZEN-MEMBER-IDENTITY-DRIFT` /
  `FETCH-PROVENANCE-DIVERGENCE`. No special-case pre-flight is needed; parse-time
  rejection *is* the pre-flight.
- **Post-cutover there is only one epoch.** `milpa fetch`/`add`/`update` all emit
  `dag-sha256:` exclusively. A lock that still contains `sha256:` was written by
  a pre-cutover binary and is simply re-locked (`milpa fetch`); milpa does not
  attempt to read, compare, or partially-migrate it. There is no "transient
  mixed-epoch lock" to reason about — any non-`dag-sha256:` entry is an error,
  not a tolerated state.

This preserves the property whose *absence* turned the original churn into a
multi-day diagnosis — with self-describing schemes the stale state names itself
(`ID-UNSUPPORTED-ALGORITHM: sha256:…`) — **without** building a legacy-support
surface to get it. The prefix does the work; nothing accommodates the old bytes.

### 3.6  What does *not* change (non-goals)

- The **trust / attestation flow** — publisher attests once, consumer verifies.
  Existing Rekor entries attest the *bytes the vendor fetched* (still a valid
  provenance record); the active `content_hash` moving to epoch 2 does not
  invalidate them. Re-attestation policy for regenerated entries is a B-cutover
  decision (§4), not a change to the flow itself.
- **Artifact-bytes identity** — rejected (§2, Escape #1).
- **Strict IPFS-CID / UnixFS compatibility** — explicitly *not* claimed.
  `dag-sha256:<hex>` is a milpa scheme string, **not an IPFS CID; it MUST NOT be
  passed to CID-parsing libraries** (F-resolved-B). milpa's content rules
  (`.git` exclusion, symlink-as-target, exec bit, no chunking) are not UnixFS;
  if the planned IPFS transport (`rfc-pluggable-fetchers` F7) ever lands, it
  defines an explicit epoch↔CID mapping then.
- **`nim.cfg` emission** — unaffected; it reads `src_dir`/`requires`, never
  `identity`.
- The **nim dogfood impl** — out of scope; inherits the authority for free.

## 4  Phases & slices

### Phase A — Authority & epoch rails

- **A0 — `milpa hash <source>` oracle (both impls).** New narrow subcommand,
  implemented as `FetcherRegistry.fetch(prov, dest=scratch)` → print
  `result.identity` → discard scratch (§3.3 — the architectural pin, calling no
  identity fn directly). Two sub-slices: **A0-parse** — a standalone
  `parse_source_spec(args) -> Provenance` (it does **not** exist today;
  `GitProvenance` is built inline in `resolver.py`/`cmd_fetch`), unit-testable in
  isolation; **A0-cmd** — the ~5-line CLI wrapper over `FetcherRegistry`. Spec
  the command in `spec/cli-contract.md` (arg forms, stdout = one identity string,
  exit-code/slug table, CAS side-effect = **pure/none**, git auth inherits
  `fetch`). The one stable SSOT delegation surface; prerequisite for A3.
  *Testable:* `parse_source_spec(["git=…","ref=…"])` returns the right
  `Provenance`; `milpa hash git=<url> ref=<commit>` prints the same identity
  `milpa fetch` writes, both impls; one conformance fixture pins it.

- **A1 — Self-describing scheme, no legacy support (spec + impls).** Define
  the canonical `dag-sha256:` prefix and make `parse_identity` **two-tier**:
  accept `CANONICAL_SCHEMES={dag-sha256}`, reject **everything else** (including
  bare `sha256:`) as `ID-UNSUPPORTED-ALGORITHM` (§3.5). No `LEGACY_SCHEMES` set,
  no new error type. **Update `ID-UNSUPPORTED-ALGORITHM`'s triggered-field text**
  so it explicitly covers a stale `sha256:` identity with the remediation
  "re-lock with `milpa fetch`". Because rejection lives in `parse_identity`, the
  `fetch`/`lock`/`verify`/`--frozen` paths (incl. the `frozen.py` member-drift +
  `contains()` paths) inherit it automatically — a stale lock fails at parse,
  before disk/CAS I/O, with no per-command special-casing. Strike the
  contradicting clauses: `spec/identity.md §1.7`, **§1.7.6**, **§2.3
  (algorithm-agility / dual-emit language)**; clarify `dep_decl_hash` stays
  `sha256:` regardless of epoch (`spec/dep-decl.md §3`). Generalize
  `cas.py` `list_identities`/`resolve_prefix`/`path_for` (+ Rust `store.rs`) to
  enumerate algorithm subdirs generically, not hardcoded `sha256/` (so the store
  is scheme-agnostic, not so it "supports" two schemes). `dag-sha256:` grammar
  defined here; epoch-2 *computation* lands in B1.
  *Testable:* both impls round-trip a `dag-sha256:` string; a `sha256:` (or any
  unknown prefix) raises `ID-UNSUPPORTED-ALGORITHM`, never a silent divergence.

- **A2 — Git-materialized identity fixtures (corpus, for milpa-py/rust).** Add
  `conformance/spec-v1/` fixtures distinguishing *git-committed bytes* from
  *archive bytes* for the same logical source: commit a file as LF in a
  git-protocol fixture; provide the same file as CRLF in a tarball fixture;
  assert they produce **different** hashes (milpa does no line-ending
  normalization, §1.6). **First audit** `fixture-296/297` — the runner passes
  `core.autocrlf=false` and H3b reads object-store bytes, so they likely do
  **not** exercise the divergence today. Closes the blind spot in *milpa's own*
  authority; epoch-2 cross-transport fixtures are B1/B2 gates.
  *Testable:* new fixtures pass under milpa-py + milpa-rust and pin the
  git-vs-archive distinction.

- **A3 — Delete tianguis's freelance hasher; delegate to `milpa hash` (cross-repo,
  code-only).** One atomic tianguis change set (no RED trunk): route **both**
  tianguis hashing call sites through `milpa hash`, each via the source form that
  matches the call site's actual transport — `vendor/driver.nim` (git shallow
  clone) via `milpa hash git=<url> ref=<sha>`, and `vendor/realdriver.nim` (OCI
  `oras pull` + extract) via `milpa hash oci=<registry>/<repo>@<digest>`. **This
  corrects the original A3 assumption that *both* drivers were git-sourced:
  `realdriver.nim` hashes an OCI-pulled tree, which is why A3 has a hard

### Phase B — Canonical Merkle-DAG identity (epoch 2, #180)

- **B1 — Spec the canonical content Merkle DAG (epoch 2).** Promote §3.4 to a
  byte-level normative table in `spec/identity.md`: neutral blob hash; tree-node
  entry encoding; **four-valued mode-byte** (`0x00`/`0x01`/`0x80`/`0x40`-tree —
  round-2 C1); the DAG-construction pseudocode incl. **per-level leaf-name sort**
  and **buffered (non-streaming) collection**; empty-tree recursion + the
  **pinned empty-root digest**; submodule splicing; name-byte ceiling (≤4096);
  the `dag-sha256:` string + 64-hex digest. **Strike the now-false `§1.7.4`
  "identity ignores the exec bit"** and update the `§3.1` CAS-layout example to
  show `dag-sha256/`. Update `spec/registry-protocol.md §3.2` to accept
  `dag-sha256:` for `content_hash`. Add epoch-2 fixtures incl. a **pinned
  non-trivially-nested tree** (≥2 levels, leaf-name order ≠ full-path order, hand-
  computed digest — the cross-impl oracle), subtree sharing, symlinks, exec bits,
  empty dirs, `.git` exclusion, submodule splicing.
  *Testable:* epoch-2 fixtures pass under both impls against the **hand-computed**
  pinned digests (not against each other); **cross-transport fixtures (git ≡
  tarball ≡ local) are blocking gates.**

- **B2-git / B2-tarball / B2-local / B2-oci — per-transport materializers.** One
  slice each, behind a single seam: `materialize(source) -> Sequence[(relpath,
  mode_byte, content_bytes)]` (buffered, §3.4); the DAG builder is a pure
  function over it. **B2-git first** (load-bearing for A3/B-cutover): split into
  (a) **extract the iterator** from the existing `materialize_git_tree`
  (~400-line disk-writing fn; `7341d34` object-store path) with current
  conformance fixtures as the net, and (b) **the DAG builder** + **decouple
  `CAStore.admit`** from its inline `compute_content_hash` (inject/precompute the
  hash). **B2-tarball** states the lossy-archive rule (zip without exec bits = a
  different tree, §3.4). **B2-oci** is a stub (coded not-implemented; no OCI
  fetcher yet). `MockedFetcher` runs the DAG builder over staged bytes (local
  path), **not** a git object store.
  *Testable per slice:* that transport yields the pinned `dag-sha256`;
  `fixture-184-cross-transport-identity` stays green across git+tarball(+local).

- **B-cutover — Corpus regen + registry regen + consumer re-lock + unblock.**
  (1) A **corpus-regeneration tool** (~150 LOC wrapping the existing
  `test_conformance` machinery) re-emits every `expected/milpa.lock` (~90+) and
  `expected/content_hash` (~6) under epoch 2 via milpa-py, then verifies milpa-rust
  byte-matches. **It must be code-reviewed as carefully as the DAG builder** (a
  wrong tool silently rewrites the authority); guard it with ≥2 **independently
  hand-computed** cross-transport pins. Include **error-fixtures whose slug
  changes** (e.g. `fixture-086-frozen-member-identity-drift` → re-pinned to a
  `dag-sha256:` drift, since a `sha256:` input now fails at parse as
  `ID-UNSUPPORTED-ALGORITHM`). (2) Regenerate
  tianguis `index.kdl` **and `index.json`** (parity) via `milpa hash`; Rekor
  policy (existing entries stay valid provenance; new/updated re-signed). (3)
  Re-lock consumers (`milpa fetch`); **unblock `amoxtli`**. (4) Emit only
  `dag-sha256:`; any leftover `sha256:` → `ID-UNSUPPORTED-ALGORITHM` (re-lock).
  Note the `<root>/sha256/` CAS subtree is now bulk garbage (a GC note for `rfc-store-gc.md`).
  *Testable:* full corpus green both impls at epoch 2; `amoxtli` `fetch`+`verify`
  green; index.kdl/json carry `dag-sha256:` in parity.

- **B-split (separate issue) — subtree dedup in the CAS.** The Merkle payoff,
  but a CAS *layout* change (per-blob / per-tree-node objects vs whole-tree
  admission), with its own `rename(2)` admission unit, path grammar (`<algo>/
  <type>/<hex>`), and GC interaction (`rfc-store-gc.md`, incl. pruning the
  epoch-1 `sha256/` garbage). Separable from identity correctness. **Filed as its
  own issue**, not a slice here.

## 5  Migration & compatibility

- **Epochs.** 0/1 = pre-cutover, both bare `sha256:` (not supported post-cutover
  → re-lock; not distinguished). 2 = canonical Merkle DAG (`dag-sha256:`), the
  only scheme milpa emits or accepts going forward.
- **One migration, no legacy support.** The registry + every lock regenerate
  **once** (B-cutover), under epoch 2. The lockfile *schema* is unchanged (only
  the identity string's prefix differs), so there is no second (schema-version)
  migration — and milpa carries **no** read-only legacy path to maintain across
  it.
- **Self-describing from A1.** After A1 every identity names its scheme; a stale
  `sha256:` hash is a coded `ID-UNSUPPORTED-ALGORITHM` (re-lock), not a silent
  `FETCH-PROVENANCE-DIVERGENCE`.
- **Last un-versioned churn.** The epoch-2 cutover is breaking (one re-lock).
  Acceptable pre-1.0 precisely because it is the *last* un-versioned change —
  after this RFC, identity evolves by migration.

## 6  Forks & notable decisions

**Resolved during round 1** (were open in the draft):
- **F-A blob hash → transport-neutral `sha256(content)`.** git-blob-reuse gives
  no real win under the neutral thesis and would break the MockedFetcher corpus
  infra. The "near-zero-cost" claim is corrected to "zero marginal I/O, one
  sha256 pass."
- **F-B digest encoding → explicit non-CID `dag-sha256:<hex>`.** "CID-shaped but
  not a CID" misleads IPFS tooling; make no CID claim.
- **F-C / dual-emit → dropped** in favor of a clean cutover; a stale `sha256:`
  is `ID-UNSUPPORTED-ALGORITHM` (§3.5), with no legacy-acceptance path.
- **Subtree dedup (was B4) → split** to its own CAS issue.

**Confirmed / fixed in round 2:**
- **§3.4 encoding declared SOUND** by the depth + design lenses **after the C1
  fix** — the mode-byte is now four-valued (`0x40` tree) so it domain-separates
  blob vs subtree children (CT-style) and can represent subdirectories at all.
- Hardening folded in: per-level **leaf-name sort** (the top cross-impl risk) with
  a hand-computed pinned nested fixture; empty-root digest; name ceiling;
  buffered (non-streaming) builder; `milpa hash` pinned to `FetcherRegistry.fetch`
  + `local=` form + `ref`-must-be-SHA; the full **spec-edit ledger** (§4); the
  A0-parse / B2-git-split / cross-repo-ordering feasibility fixes.

**Corrected post-round-2 (Corey, "no legacy support pre-v1"):** the draft's
read-only legacy apparatus is **removed entirely** — no `LEGACY_SCHEMES` tier, no
`ID-LEGACY-SCHEME` error, no `--frozen` legacy pre-flight, no mixed-epoch lock
tolerance, no `[legacy — re-lock]` annotation. `parse_identity` is **two-tier**
(`dag-sha256:` canonical, everything else `ID-UNSUPPORTED-ALGORITHM`). The
self-describing-prefix value of P3 is retained for free (a stale `sha256:` is a
*coded* unsupported error, not a silent divergence); the accommodation machinery
is what's gone. §3.2/§3.5/§5/A1/B-cutover/ledger all updated.

**Notable decisions — applied; flag if you disagree:**
- **N1 — SSOT mechanism = delegate via a new `milpa hash` oracle** (§3.3), *not*
  a corpus-gated native Nim hasher. Round 2 re-examined and kept it, pinning the
  oracle to `FetcherRegistry.fetch` so it cannot become a fresh divergence.
- **N2 — Epoch 2 includes the executable bit in identity** (§3.4 four-valued
  mode-byte), a deliberate semantic correction over epoch 1. Aligns with git +
  tianguis's existing hasher; fixes a real correctness hole (loss of `+x`).
- **N3 — Strike the spec's existing dual-emit "algorithm agility" (§2.3), and
  carry no legacy support at all.** The spec already *anticipated* algorithm
  migration via dual-emit; this RFC overrides it with a clean cutover, and
  (per Corey) goes further: **no read-only legacy tier either** — a post-cutover
  `sha256:` is `ID-UNSUPPORTED-ALGORITHM`, not a specially-handled legacy state.
  Pre-v1, single controlled consumer, breaking fine; the one-shot B-cutover regen
  is the whole migration. Algorithm-agility-by-*migration* remains the model;
  dual-emit / legacy-acceptance can return if/when there are external consumers +
  a v1 commitment. *Confirmed by Corey.*

**Open forks:** none blocking. The §3.4 byte table (B1) is the last cheap-to-change
artifact; it is now reviewed-sound, so /tdd continues (N1/N2/N3 stand).
