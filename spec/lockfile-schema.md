# milpa lockfile schema (S5)

Normative spec of `milpa.lock` — the reproducible-build snapshot — and
`nim.cfg` — the compiler path configuration emitted from a resolved graph.
Every parser and emitter that claims milpa conformance MUST implement the rules
marked `> NORMATIVE:`. Items marked `> NOTE:` describe the reference Python
implementation; conformant alternatives MAY differ in those details.

This document covers the **lockfile KDL grammar**, **version negotiation**,
**tarball TOFU pinning**, **nim.cfg emission**, and **verification semantics**.
Related specs:

- `spec/errors.md` — every error code this module can produce
- `spec/manifest-grammar.md` (S4) — manifest provenance-descriptor model
- `spec/resolver-semantics.md` (S6) — frozen fast-path + prior-lockfile
  pin reuse behavior
- `spec/identity.md` (S12) — content-hash canonical algorithm (cross-ref;
  not duplicated here)

---

## Normative surface

A conformant implementation of this spec MUST:

1. Write and read `milpa.lock` as valid KDL 2.0.
2. Emit a top-level `version` integer node whose value equals
   `LOCKFILE_SCHEMA_VERSION` (currently `1`).
3. Raise `LOCK-VERSION-MISSING` when `version` is absent from a lockfile being
   parsed; raise `LOCK-VERSION-UNSUPPORTED` when the integer is not `1`.
4. Sort dep entries lexicographically by name in the emitted lockfile so the
   same resolved graph always produces byte-identical text. Sort `requires`
   args lexicographically by name as well (see §3.4 and `resolver-semantics.md`
   §4.4).
5. Emit a `provenance { }` block per dep using the exact field names defined in
   §3 for each kind (`git`, `tarball`, `local`, `member`, `oci`).
6. Validate the `identity` field against the multihash format
   (`<algorithm>:<hex>`) on parse; raise `LOCK-DEP-IDENTITY-INVALID` on
   malformed values.
7. On first fetch of a tarball dep without a declared `sha256`: record the
   computed archive sha256 into the lockfile receipt. Subsequent reads of that
   lockfile pin the archive hash. This is normative TOFU first-use pinning, not
   an optional optimization.
8. Emit `nim.cfg` with POSIX path separators regardless of host OS.
9. Emit `nim.cfg` in the order: (1) self src-dir path, (2) dep `--path:` lines,
   (3) feature-flag `-d:` lines — each group absent if empty.
10. Apply the `<dep_name>_<flag_name>` define convention for feature flags
    unless the dep declares an explicit override mapping.
11. Emit exactly one top-level `strategy` node per lockfile (see §2.2).

## 1  Document format and file name

> NORMATIVE: `milpa.lock` MUST be a valid [KDL 2.0](https://kdl.dev) document.
> A parser MUST reject documents that do not conform to KDL 2.0 syntax and
> raise `LOCK-KDL-SYNTAX`.

> NORMATIVE: The canonical lockfile file name is `milpa.lock` in the project
> root directory (the same directory as `milpa.kdl`).

> NOTE: The reference implementation writes the file via `write_lockfile`
> (`lockfile.py`), which calls `path.parent.mkdir(parents=True, exist_ok=True)`
> before writing.

---

## 2  Top-level structure

A `milpa.lock` document consists of the following top-level nodes, in the
order emitted:

```kdl
// generated by milpa; reproducible build snapshot
version 1
strategy "maxver"

dep "depname" { ... }
dep "depname2" { ... }
```

### 2.1  `version` node

> NORMATIVE: A lockfile MUST contain exactly one top-level `version` node
> carrying exactly one integer argument. Its absence MUST raise
> `LOCK-VERSION-MISSING`. Wrong arity raises `LOCK-FIELD-ARITY`. A non-integer
> value raises `LOCK-FIELD-TYPE`.

> NORMATIVE: The `version` integer identifies the lockfile schema epoch. The
> current spec defines only schema version `1`. A parser MUST raise
> `LOCK-VERSION-UNSUPPORTED` for any `version` value other than `1`. No
> best-effort or partial parse MAY be attempted on an unrecognized version.

> NORMATIVE: `LOCKFILE_SCHEMA_VERSION` (the integer `1`) and the manifest
> `spec-version` epoch (also currently `1`) are **related but distinct
> namespaces**. `LOCKFILE_SCHEMA_VERSION` governs the lockfile KDL format.
> `spec-version` in `milpa.kdl` governs the manifest grammar epoch. A v2
> lockfile schema requires an amendment to this spec; a manifest spec-version
> bump does not automatically bump the lockfile schema version, nor vice versa.

> NOTE: The reference implementation raises `LockfileError` (with the
> `.code` field set) in both missing-version and unsupported-version cases
> (`lockfile.py:parse_lockfile`, lines 311–321).

### 2.2  `strategy` node

> NORMATIVE: A lockfile MUST contain exactly one top-level `strategy` node
> carrying one string argument naming the resolution strategy used to produce
> this lockfile (e.g. `"maxver"`). A conformant emitter always writes this node;
> the parser MUST still default to `"maxver"` when the node is absent, to
> tolerate any pre-v1.0 lockfiles that predate this requirement.

> NOTE: `strategy` is recorded for diagnostics and for the frozen fast-path
> strategy-match check (`FROZEN-STRATEGY-MISMATCH`). It does not change how the
> lockfile is parsed.

### 2.3  `dep` nodes

> NORMATIVE: Each resolved dep MUST be emitted as exactly one top-level `dep`
> node carrying exactly one positional string argument (the dep name). A missing
> or non-string argument MUST raise `LOCK-DEP-NAME-ARITY`.

> NORMATIVE: Dep nodes MUST be sorted lexicographically by name in the emitted
> file. The same resolved graph MUST always produce byte-identical lockfile
> text.

### 2.4  Canonical serialization

> NORMATIVE: A conformant emitter MUST produce byte-identical output for the
> same logical lockfile, following these rules exactly. A Rust (or any other)
> reimplementation that claims conformance MUST reproduce every byte of this
> layout.
>
> **File-level structure:**
>
> 1. Line 1: the literal comment `// generated by milpa; reproducible build snapshot`
> 2. Line 2: `version 1` (the integer, unquoted, no leading/trailing spaces)
> 3. Line 3: `strategy "<strategy-name>"` (the strategy string, double-quoted)
> 4. Line 4: blank
> 5. For each dep (sorted lexicographically by name):
>    a. `dep "<name>" {`  
>    b. The dep's child fields (see below).
>    c. `}`  
>    d. Blank line.
> 6. The file ends after the blank line that follows the last dep block.
>    The final byte in the file is a newline (`0x0A`).
>
> **Dep-block child field layout (4-space indent):**
>
> - `    identity "<sha256:64hex>"` — emitted only when `identity` is not null.
> - `    version "<semver>"` — always emitted.
> - `    src_dir "<path>"` — always emitted (empty string → `src_dir ""`).
> - `    requires` (bare, no arguments) when the dep has no transitive deps;
>   otherwise `    requires "<dep1>" "<dep2>" ...` with args in lexicographic
>   order, space-separated, each double-quoted.
> - `    active_flags "<f1>" "<f2>" ...` — emitted only when non-empty; args
>   are double-quoted and space-separated.
> - `    self_mirrors (url)"<url1>" (url)"<url2>" ...` — emitted only when
>   non-empty; each URL is `(url)`-annotated and double-quoted (the `(url)`
>   annotation is NOT used for other URL-valued fields such as git `url`,
>   tarball `url`, or OCI `registry`/`repository`/`digest`).
> - `    provenance {` — the provenance block open.
> - Provenance child fields at **8-space indent** (see below).
> - `    }` — the provenance block close.
>
> **Provenance child field layout (8-space indent):**
>
> - All provenance field values are double-quoted strings.
> - `kind` is always first.
> - Fields are emitted in the order defined per kind in §4 (git: kind/url/ref/
>   commit_sha; tarball: kind/url/sha256; local: kind/path; member: kind/name;
>   oci: kind/registry/repository/digest).
> - Optional fields (`ref`, `commit_sha`, `sha256`) are omitted entirely when
>   null — no null literal, no empty string.
>
> **All string values are double-quoted** with no escaping beyond what KDL 2.0
> requires (backslash-escaping of `\`, `"`, and control characters). No
> single-quoted strings, no raw strings (`#"..."#`), no integer types except
> the top-level `version` node.

> NOTE: The reference Python `format_lockfile` performs this escaping via the
> single `_kdl_str` helper (every emitted string value passes through it). The
> conformance fixture `fixture-118-lock-string-escaping` exercises a dep `ref`
> containing both `"` and `\` and pins the escaped `expected/milpa.lock`, so the
> requirement is now observable in the suite. (Historical: pre-P3 the Python
> reference interpolated raw strings — a latent defect, reconciled here. All
> implementations MUST escape.)

> NOTE: The reference implementation is `format_lockfile` and
> `_format_provenance_fields` in `lockfile.py`. The final text is produced by
> `"\n".join(lines)` where the `lines` list always ends with `["}", ""]` for
> the last dep block — this yields `}\n` as the final two characters (the
> trailing blank entry in the list contributes the last `\n` when joined).

## 3  Per-dep record structure

Each `dep` node contains the following child nodes:

```kdl
dep "depname" {
    identity "sha256:<64-hex>"
    version "1.2.3"
    src_dir "src"
    requires "dep1" "dep2"
    active_flags "flag1"          // omitted when empty
    self_mirrors (url)"https://..." // omitted when empty
    provenance {
        kind "git"
        url "https://..."
        ref "main"
        commit_sha "abc123..."
    }
}
```

### 3.1  `identity` field

> NORMATIVE: When present, `identity` MUST carry exactly one positional string
> argument in multihash-encoded form: `<algorithm>:<digest-hex>`. Currently only
> `sha256` is supported; the digest MUST be exactly 64 lowercase hexadecimal
> characters. A malformed value MUST raise `LOCK-DEP-IDENTITY-INVALID`.

> NORMATIVE: `identity` records **what** a dep is — the content hash of its
> source tree, independent of how or where it was fetched. It is the field
> consumers verify against. It MUST NOT encode provenance information.

> NOTE: `identity` may be `null` / absent for deps that have not yet been
> content-hashed (Phase A partial). The reference parser accepts absent or
> `None` values and stores `None` in `LockedDep.identity`.

> NOTE: The identity algorithm (canonical byte stream, POSIX relpath sort, mode
> encoding, `.git/` exclusion, multihash prefix) is specified in
> `spec/identity.md` (S12). The lockfile records the output; it does not
> re-specify the algorithm.

### 3.2  `version` field

> NORMATIVE: `version` MUST carry exactly one positional string argument in
> semver form: `MAJOR.MINOR.PATCH` optionally followed by a pre-release
> identifier (`-pre`) and/or build metadata (`+build`). Wrong arity or
> non-string raises `LOCK-DEP-FIELD-ARITY`. The parse default when the
> `version` node is absent is `"0.0.0"`.

> NORMATIVE: A conformant emitter MUST write the placeholder version `"0.0.1"`
> for non-named dep kinds (url/tarball/local/member/oci), because they are
> resolved by identity rather than version constraint. Named deps MUST carry
> the actual resolved version string from the tianguis index.

> NOTE: The two values serve distinct roles: `"0.0.0"` is the parser's
> default for a missing node (read path only); `"0.0.1"` is the canonical
> placeholder emitted by the writer for non-versioned dep kinds (write path).
> A conformant implementation always writes `"0.0.1"` for these dep kinds
> and therefore never produces a lockfile where parsing a present
> `version "0.0.1"` node falls back to the missing-node default.

### 3.3  `src_dir` field

> NORMATIVE: `src_dir` MUST carry exactly one positional string argument (the
> relative path from the dep root to its Nim source directory). An empty string
> means the dep root is also the source root. Wrong arity or non-string raises
> `LOCK-DEP-FIELD-ARITY`.

### 3.4  `requires` field

> NORMATIVE: `requires` carries zero or more positional string arguments, each
> being the name of a direct transitive dep. When no transitive deps exist,
> `requires` MUST still be emitted with no arguments (bare `requires` node).
> The arguments MUST be sorted lexicographically by dep name. See
> `resolver-semantics.md` §4.4 (canonical emission order) for the unified
> ordering rule that governs both dep entries and `requires` args.

> NOTE: The reference implementation sorts `requires` in `_locked_from_resolved`
> via `tuple(sorted(d.requires))` (`lockfile.py`). This ensures that parallel
> fetch runs, which accumulate `requires` in non-deterministic BFS arrival
> order, always produce byte-identical output.

### 3.5  `active_flags` field (optional)

> NORMATIVE: `active_flags` carries zero or more positional string arguments,
> each being the name of a feature flag active for this dep in the resolved
> graph. MUST be omitted from the emitted KDL when no flags are active, to
> keep diffs minimal.

### 3.6  `self_mirrors` field (optional)

> NORMATIVE: `self_mirrors` carries zero or more URL arguments. Each URL MAY
> be either a plain string or a `(url)`-annotated value; both forms MUST be
> accepted on parse and normalized to plain URL strings. MUST be omitted from
> the emitted KDL when empty.

> NOTE: Self-mirrors are URLs declared by the dep's own `milpa.kdl` as
> alternative fetch locations (issue #79). They are cached in the lockfile so
> subsequent resolves can fall back to them even when the primary fetch fails
> before discovery.

## 4  Provenance block

Each dep contains exactly one `provenance { }` block (multi-provenance per
issue #37 is reserved for a future amendment). The block's children are scalar
fields.

> NORMATIVE: Every provenance block MUST contain a `kind` child node carrying
> exactly one string argument — the provenance kind discriminator. A missing
> `kind` MUST raise `LOCK-PROV-KIND-MISSING`. An unknown `kind` value MUST
> raise `LOCK-PROV-KIND-UNKNOWN`.

> NORMATIVE: Each child node within a provenance block MUST carry exactly one
> value. Wrong arity raises `LOCK-PROV-FIELD-ARITY`. A required field absent
> from a block raises `LOCK-PROV-FIELD-MISSING`.

The following subsections define each provenance kind. Fields listed as
*required* MUST be present; fields listed as *optional* MAY be absent and
default to `null`.

### 4.1  `git` provenance

Used for `git=...` URL deps and named deps resolved via the tianguis index to a
git URL.

| Field | Required | Type | Semantics |
|---|---|---|---|
| `kind` | yes | `"git"` | discriminator |
| `url` | yes | string | git remote URL |
| `ref` | no | string | branch/tag/ref as declared in the manifest |
| `commit_sha` | no | string | resolved commit SHA after fetch |

> NORMATIVE: `url` is required; its absence raises `LOCK-PROV-FIELD-MISSING`.
> `ref` and `commit_sha` are optional and MUST be omitted from the emitted KDL
> when `null`.

> NOTE: `commit_sha` is the resolved SHA from the fetch receipt (`d.sha`), not
> the manifest's declared ref. It may be `null` for deps that were not actually
> fetched in this run (e.g., frozen fast-path cache hits).

### 4.2  `tarball` provenance

Used for `tarball=...` deps.

| Field | Required | Type | Semantics |
|---|---|---|---|
| `kind` | yes | `"tarball"` | discriminator |
| `url` | yes | string | archive download URL |
| `sha256` | no | string | archive sha256 hex digest (TOFU receipt) |

> NORMATIVE: `url` is required. `sha256` is optional on first fetch (TOFU
> model — see §5); once pinned it MUST be recorded and preserved on all
> subsequent lockfile writes for this dep.

### 4.3  `local` provenance

Used for `local=...` deps (local filesystem path).

| Field | Required | Type | Semantics |
|---|---|---|---|
| `kind` | yes | `"local"` | discriminator |
| `path` | yes | string | as-declared relative path from project root |

> NORMATIVE: `path` records the path string **exactly as declared** in the
> manifest (relative to the project root). It MUST NOT be resolved to an
> absolute path. This preserves portability across machines within the same
> workspace layout.

### 4.4  `member` provenance

Used for workspace-internal member references (`member "name"` dep form).

| Field | Required | Type | Semantics |
|---|---|---|---|
| `kind` | yes | `"member"` | discriminator |
| `name` | yes | string | workspace member name |

### 4.5  `oci` provenance

Used for OCI-artifact deps resolved via the tianguis index to an OCI registry.

| Field | Required | Type | Semantics |
|---|---|---|---|
| `kind` | yes | `"oci"` | discriminator |
| `registry` | yes | string | OCI registry hostname |
| `repository` | yes | string | repository path within the registry |
| `digest` | yes | string | immutable content-addressed digest pin |

> NORMATIVE: All three fields — `registry`, `repository`, `digest` — are
> required; the absence of any raises `LOCK-PROV-FIELD-MISSING`.

### 4.6  `registry` provenance (read-compat only)

> NOTE: The `registry` kind was emitted by milpa prior to issue #97. The
> writer never emits it any longer — named deps now resolve to `git` or `oci`
> records via the tianguis index. The parser MUST still accept `registry`
> provenance blocks in existing lockfiles to preserve read-compat. The
> `RegistryProvenanceRecord` dataclass is retained until straggler old lockfiles
> are regenerated; it will be removed in a future schema version.

Fields: `kind "registry"`, `name` (required), `tag` (optional), `commit_sha`
(optional). A lockfile containing a `registry` provenance entry on the frozen
fast-path raises `FROZEN-LEGACY-REGISTRY-PROVENANCE` — the user must run
`milpa update <name>` to re-resolve via tianguis.

## 5  Tarball TOFU first-use pinning

> NORMATIVE: A tarball dep declared **without** a `sha256=` property in the
> manifest (i.e. `TarballProvenance.expected_sha256 is None`) undergoes
> **first-use pinning** (TOFU — Trust On First Use): on the first fetch, the
> fetcher downloads the archive, computes its sha256 hex digest, and records
> that value as the `sha256` field of the `tarball` provenance block in the
> lockfile. All subsequent fetches using this lockfile MUST supply the recorded
> `sha256` as the expected hash and MUST raise `FETCH-SHA256-MISMATCH` if the
> archive does not match.

> NORMATIVE: This is normative first-use pinning, not an incidental
> optimization. An implementation that skips recording the archive sha256 on
> first fetch violates this spec.

> NOTE: The distinction between the archive sha256 (provenance receipt) and
> the content hash (identity) is critical: `sha256` in the tarball provenance
> block records the hash of the **downloaded archive bytes** (a transport
> integrity check). The `identity` field records the hash of the **extracted
> source tree** after any `strip_components` processing. They are orthogonal
> fields and MUST NOT be confused.

> NORMATIVE: `strip_components` (from the manifest's `TarballDep`) determines
> which paths enter the extracted tree. Content-hash computation (`identity`)
> MUST be performed **after** stripping, on the stripped tree. This is a
> manifest-layer normative claim cross-referenced here because it directly
> affects what the lockfile's `identity` value represents for a tarball dep.
> See `manifest-grammar.md` §3.2 (TarballDep grammar), §4.2 (tarball provenance
> kind), and `identity.md` for the algorithm.

> NOTE: `strip_components` is a manifest-layer parameter — it is read from
> `milpa.kdl` at fetch time and is NOT stored in the lockfile. The frozen
> fast-path reads `strip_components` from the live manifest, not from the
> lockfile.

> NOTE: The git `ref` field is required in the tianguis index per
> `registry-protocol.md` §3.3, but is optional in the lockfile (the resolved
> commit SHA is the durable pin; `ref` is recorded for human readability and
> diagnostics only).

## 6  Verification semantics

milpa exposes two verification operations. Both are normatively specified here
at the contract level; implementation detail is incidental.

### 6.1  Graph-vs-lockfile verification (`verify_against_graph`)

> NORMATIVE: After resolution, a conformant impl MUST verify that the resolved
> graph matches the lockfile dep-for-dep. Specifically:
>
> - Every dep in the resolved graph MUST have a corresponding entry in the
>   lockfile (by name). A dep present in the graph but absent from the lockfile
>   is a mismatch.
> - Every dep in the lockfile MUST have a corresponding entry in the resolved
>   graph. A dep present in the lockfile but absent from the graph is a
>   mismatch.
> - For every dep present in both: the `identity` fields MUST match exactly.
>
> Any mismatch MUST raise `LOCK-GRAPH-MISMATCH`.

> NOTE: The reference implementation performs this check in
> `verify_against_graph` (`lockfile.py:587–613`). It uses set-difference on the
> name keys of the two collections.

### 6.2  Disk-vs-lockfile verification (`verify_lockfile_against_deps`)

> NORMATIVE: The `milpa verify` command MUST check that every dep in the
> lockfile is present on disk under `_deps/<name>/` and that its content hash
> matches the lockfile's recorded `identity`. For each dep:
>
> - If `_deps/<name>/` is absent: report a divergence.
> - If `_deps/<name>/` is not a directory: report a divergence.
> - If the computed `content_hash(_deps/<name>/)` differs from the lockfile's
>   `identity`: report a divergence.
>
> Additionally, any directory under `_deps/` (excluding hidden entries starting
> with `.`) that has no corresponding lockfile entry MUST be reported as an
> extra dep.

> NORMATIVE: Divergences MUST be collected and returned as a list; verification
> MUST NOT stop at the first mismatch. The caller decides whether to treat
> divergences as a hard error.

### 6.3  Workspace-aware verification

> NORMATIVE: In a workspace context, deps with `member` provenance route to the
> workspace member's directory for identity verification (not to
> `_deps/<name>/`). All other dep kinds route to `_deps/<name>/` in the
> workspace root.

## 7  `nim.cfg` emission

> NOTE: `nim.cfg` emission is included in this document because the conformance
> fixtures list `nim.cfg` as an expected output alongside `milpa.lock`, making
> it a cross-impl commitment tied to the same lockfile/resolver output layer.
> It could be split to a `nim-cfg.md` in a future amendment; for spec v1.0 it
> lives here.

`nim.cfg` is a declarative Nim compiler configuration file written at the
consuming project's root. The Nim compiler reads it automatically on startup.
milpa writes `--path:` directives pointing at each resolved dep's source
directory so `import <dep>` resolves without nimble involvement.

> NORMATIVE: milpa MUST NOT generate `config.nims` — that file uses NimScript.
> `nim.cfg` is the only compiler-configuration output. See
> `docs/decision-config-nims.md`.

### 7.1  File header

> NORMATIVE: `nim.cfg` MUST begin with exactly this three-line header comment,
> followed by exactly one blank line, before any `--path:` line:
>
> ```
> # generated by milpa; do not edit
> # manifest: milpa.kdl
> # lockfile: milpa.lock
>
> ```
>
> (The header uses `#` comments — `nim.cfg`'s comment syntax — whereas
> `milpa.lock` uses `//`.) The header is emitted unconditionally, even when the
> graph has no deps. The committed `expected/nim.cfg` fixtures encode these
> exact bytes; the byte-diff makes the header de-facto mandatory, so it is
> stated normatively here.

### 7.2  Path separator

> NORMATIVE: All `--path:` lines in `nim.cfg` MUST use POSIX path separators
> (`/`) regardless of host OS. Nim's compiler configuration syntax is
> OS-agnostic; using host-native separators on Windows would produce
> non-portable files.

### 7.3  `--path:` line form

> NORMATIVE: Each dep contributes exactly one `--path:` line:
>
> ```
> --path:"<deps_dir>/<name>[/<src_dir>]"
> ```
>
> where:
> - `<deps_dir>` is the relative or absolute path to the deps directory
>   (default `_deps`), serialized with POSIX separators.
> - `<name>` is the dep name.
> - `/<src_dir>` is appended only when `src_dir` is non-empty.

### 7.4  Emission order

> NORMATIVE: Lines MUST be emitted in the following order:
>
> 1. **Self src-dir path** — `--path:"<self_src_dir>"` — emitted once, before
>    all dep paths, when the consuming package has a non-empty `src_dir`. This
>    ensures self-modules shadow any same-named dep import paths.
> 2. **Dep `--path:` lines** — one per dep in the resolved graph, **sorted
>    lexicographically by dep name** (the single emission-order rule; see
>    `resolver-semantics.md` §4.4).
> 3. **Feature-flag `-d:` lines** — one per active flag per dep (see §7.5),
>    separated from the path block by a blank line when non-empty.
>
> Groups (1) and (2) are omitted when empty (no self src-dir / no deps). Group
> (3) is omitted when no deps have active flags. These groups govern the
> `--path:`/`-d:` *body* only — the file-level header (§7.1) is always emitted
> regardless, so a no-deps `nim.cfg` is still the header + blank line, never an
> empty file.

> NOTE: The reference implementation ends the file with a single trailing
> newline character (the final `\n` of the joined output) — **not** a blank
> line (`\n\n`) (`nimcfg.py:58–59`).

### 7.5  Feature-flag defines

> NORMATIVE: For each dep in the resolved graph, for each flag name in
> `dep.active_flags`:
>
> - If the dep's `flag_defines` mapping contains an explicit override for this
>   flag name, emit each define string in that override as a `-d:<string>` line.
> - Otherwise emit a single `-d:<dep_name>_<flag_name>` line.
>
> This is the `<dep>_<flag>` define convention. It is normative: a conformant
> implementation MUST use this convention when no explicit override is declared.

### 7.6  Workspace per-member `nim.cfg`

> NORMATIVE: In a workspace, each member MUST receive its own `nim.cfg` at
> `<member_directory>/nim.cfg`. Each member's file lists only the deps in the
> member's **transitive closure** (deps reachable from that member's `requires`
> chain), not the full workspace graph.

> NORMATIVE: In workspace `nim.cfg` files, `--path:` lines MUST use paths
> **relative to the member's directory**, not absolute paths or workspace-root-
> relative paths.

> NORMATIVE: Relative paths in workspace `nim.cfg` files MUST use POSIX
> separators regardless of host OS.

> NORMATIVE: For a dep that is itself a workspace member, the `--path:` target
> MUST resolve to that member's directory (with `src_dir` appended if non-empty)
> rather than to `<root>/_deps/<name>/`. External deps always route to
> `<root>/_deps/<name>/`.

> NOTE: The reference implementation computes relative paths via
> `os.path.relpath(dep_target, member.directory)` and then normalizes with
> `Path(rel).as_posix()` (`nimcfg.py:161–163`). The transitive closure walk is
> in `member_dep_closure` (`nimcfg.py:94–124`), which excludes the member
> itself from its own `--path:` lines (a package does not add its own source
> to the compiler search path via `nim.cfg`).

## Appendix B — Error codes

All error codes in this section are defined in `spec/errors.md`.

**Lockfile parse errors:**

| Code | Condition |
|---|---|
| `LOCK-KDL-SYNTAX` | Input is not valid KDL 2.0 |
| `LOCK-VERSION-MISSING` | Top-level `version` node absent |
| `LOCK-VERSION-UNSUPPORTED` | `version` value is not `1` |
| `LOCK-FIELD-ARITY` | Top-level scalar field has wrong arity |
| `LOCK-FIELD-TYPE` | Top-level scalar field has wrong type |
| `LOCK-DEP-NAME-ARITY` | `dep` node missing or has non-string name arg |
| `LOCK-DEP-FIELD-ARITY` | Dep child field has wrong arity or non-string value |
| `LOCK-DEP-IDENTITY-INVALID` | `identity` value fails multihash validation |
| `LOCK-PROV-FIELD-ARITY` | Provenance child field has wrong arity |
| `LOCK-PROV-KIND-MISSING` | `kind` discriminator absent from provenance block |
| `LOCK-PROV-KIND-UNKNOWN` | `kind` value is not in the known set |
| `LOCK-PROV-FIELD-MISSING` | Required provenance field absent |
| `LOCK-FILE-NOT-FOUND` | Lockfile path does not exist |
| `LOCK-FILE-UNREADABLE` | OS error reading lockfile |

**Verification errors:**

| Code | Condition |
|---|---|
| `LOCK-GRAPH-MISMATCH` | Resolved graph and lockfile dep sets or identities diverge |

**Fetch integrity (tarball TOFU):**

| Code | Condition |
|---|---|
| `FETCH-SHA256-MISMATCH` | Downloaded archive sha256 ≠ lockfile-pinned expected sha256 |

**Frozen fast-path errors (cross-reference `resolver-semantics.md` S6):**

| Code | Condition |
|---|---|
| `FROZEN-LEGACY-REGISTRY-PROVENANCE` | Lockfile entry has `registry` provenance; re-resolve required |
| `FROZEN-STRATEGY-MISMATCH` | Requested strategy differs from lockfile's recorded strategy |
